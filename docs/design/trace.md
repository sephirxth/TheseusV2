## 0. 人怎么调它

> 这一节从需求文档挪过来。**它属于这里，不属于那边**——需求只说"我要做什么"，"怎么做"是设计。
> 2026-08-08 游渊：「不要都用这种命令行方式的实现吧？在用户用例里应该不规定实现？」

### 0.1 这个模块是两个动作、一份东西

| | 是什么 | 覆盖哪些用例 |
|---|---|---|
| **痕迹** | 留下的那份东西（名词） | —— |
| **留痕** | 写它 | **只有 U12** |
| **回忆** | 读它 | **其余七条全是**（U7 / U8 / U9 / U10 / U11 / U13 / U14） |

之前有个观察是"八条里只有一条是写的，比例不对劲"。**现在知道那不是比例失衡，是两件不同的事被塞进了一个词里。**

### 0.2 动作叫什么：**追踪**（2026-08-09 游渊定）

**中文动作 = 追踪。英文对应 `trace`——作为动词。**

这不是走回头路。之前否掉 `theseus trace` 是因为**我把它当名词用**（痕迹＝存下来的那份东西），拿"东西"给"动作"命名。**现在它是动词，指的是人在干的事，意思正好对上。**

走到这一步之前否掉过两个，两次是同一个毛病的两种形态：

| 否掉的 | 毛病 | 谁否的 |
|---|---|---|
| `why` | 拿**疑问词**命名，而疑问词只有一个方向——U7 往回问、U8 往前问，一个词装不下两个方向 | 游渊，2026-08-08 |
| `trace`（**当名词用**） | 拿**存下来的那份东西**命名，不是拿**人在干的事**命名 | 游渊，2026-08-08 |

**留下的教训**：给动作命名就用动词，别拿它操作的东西凑数。

**U9（看最近发生了什么）不单独给一个词**（2026-08-09 游渊定）。同一个动作，不带参数就是"追踪一下最近"。**少一个词，比多一个准确的词值钱。**

### 0.3 入口不止一个

需求文档现在明确不预设终端。**至少三种入口都该成立**：终端、面板、以及**直接跟 agent 说一句话**。

最后一种对 Theseus 尤其要紧——**这个系统的主要交互面本来就是对话**。设计时要保证这三种入口走的是同一套底下的东西，不是三份各写一遍。

**验**：同一件事，三种入口问出来的结果必须一致。

## 0.6 那 78.8% 查到底落在"时钟到点"的，不是一个新问题

**先按第一原则问一句：这是新问题吗？——不是。**

看清楚那条链子记的是什么：

```
时钟到点  →  开始主动思考  →  决定要干这件事  →  任务
```

**它记的是「谁触发了它」，没记「它为什么这么决定」。** 时钟触发了那次思考，但那次思考**凭什么得出这个结论**——链子里没有。

而"决定本身要留下来，还要留下它当时凭什么这么定"——**那正是 U8 的原话。**

| | 归谁管 |
|---|---|
| **新记的** | **U8 管着**。每一步带上自己的依据，链子落在时钟上就不再是问题——因为每一跳都自己说得清 |
| **旧的那批** | **补不回来。** 当时没记的依据，现在造不出来；硬造出来的因果比没有更糟。限制已明写在需求文档 U13 里 |

**留下的教训**：一个看起来棘手的新问题，先去已有的需求里找一遍——**这次它已经被覆盖了，只是换了个样子出现。**

## 0.5 底座：SQLite（2026-08-09 定）

> **这是实现，该由实现方定，不该拿去问游渊。** 我之前把它列进"等你决定"是把自己的活推出去。
> 定完写在这儿，理由摆出来，看着不对再否。

**只有两个真候选**：一个文件一行一条（旧系统那样，JSONL），或者 SQLite。

| 要做到的事 | 一行一条 | SQLite |
|---|---|---|
| 追一条因果链（U7） | 每往回跳一步就要扫一遍文件 | **一句递归查询走完全程** |
| 不重（同一件事不记两遍） | 自己写去重逻辑 | **唯一约束，数据库替你挡** |
| 不丢半条（写一半崩了） | 有可能留下半行 | **事务：要么整条进去，要么当没发生** |
| 边写边读 | 读到写一半的行 | **WAL：读的人看到的永远是完整状态** |
| 翻的代价不涨（U11） | 只能全扫，文件多大就扫多久 | **索引** |
| 自包含（VISION） | 一堆文件 | **一个文件** |

**那四件"痕迹不能丢、不能重"的硬约束**（需求文档里说它不配当用例、只能当前提的那条），**在 SQLite 这边全是现成的，在文件那边全要自己写。**

**一个例外要写清楚**：15G 对话正文**不进库里的行**。那些是大块文本，塞进去会让库本身变成 U11 的病灶。库里存**指针 + 全文索引**，正文留在磁盘上。

**★ 顺带说明**：这不是"新技术"。SQLite 就是一个文件加一套查询，没有服务、没有守护进程、没有端口——**它比自己写一套文件读写更接近"自包含"，不是更远。**

# 一、一条痕迹长什么样

```sql
CREATE TABLE trace (
  id       TEXT PRIMARY KEY,              -- ULID：按时间排序的唯一号
  ts       TEXT NOT NULL,                 -- 什么时候
  actor    TEXT NOT NULL,                 -- 谁干的：namespace:type:session
  type     TEXT NOT NULL,                 -- 什么事：task.requested 这种
  cause    TEXT REFERENCES trace(id),     -- 上一步是哪条；空 = 这是个起点
  routine  INTEGER NOT NULL DEFAULT 0,    -- 1 = 例行公事
  payload  TEXT NOT NULL,                 -- 正文（JSON）
  idem     TEXT UNIQUE,                   -- 幂等键；空的不参与去重

  CHECK (cause IS NULL OR cause < id)     -- 因必须早于果
);
```

**七个字段。旧系统是九个，删了两个。**

| 字段 | 为什么要它 | 谁的做法 |
|---|---|---|
| `id` | 要能在别处引用一条痕迹（L2 文档里的锚就是这么用的） | **ULID**——按时间排序、不需要任何协调就能保证唯一。比"时间戳＋随机数"干净 |
| `cause` | **U7/U8 的全部重量都压在这一个字段上。** 没有它，痕迹只是一堆事件；有了它，才是链子 | **git 的 commit parent**：每条指向它的上一条，往回走就是历史 |
| `routine` | U9：96% 是噪音，得有办法默认不看它们 | **syslog 的级别**（1980 年代就有）。见第三节 |
| `idem` | U12：同一件事被记两遍等于骗自己 | **Stripe 的幂等键**。见第四节 |
| `CHECK (cause < id)` | **因必须早于果**。ULID 按时间排序，所以这是一句纯字符串比较——**却让因果成环从结构上不可能** | 因果序（Lamport）。**这一条是白捡的：一句 CHECK，换掉了本来要写的环检测** |

**删掉的两个**：

| 删了 | 为什么 |
|---|---|
| `session` | 它就是 `actor` 的第三段，重复存一遍。真要按会话查，用生成列加索引，不多存一份 |
| `seq` | 旧系统用它排序。**ULID 本身就有序，这个字段没用了** |

> **简化准则**：能删的都删了。九个字段变七个，**没有任何一个用例因此做不到**。

# 二、因果链怎么走（U7 / U8）

**往回问"为什么发生"——一句话：**

```sql
WITH RECURSIVE chain(id, ts, actor, type, cause, payload, depth) AS (
  SELECT id, ts, actor, type, cause, payload, 0
    FROM trace WHERE id = :起点
  UNION ALL
  SELECT t.id, t.ts, t.actor, t.type, t.cause, t.payload, chain.depth + 1
    FROM trace t JOIN chain ON t.id = chain.cause
   WHERE chain.depth < 64
)
SELECT * FROM chain;
```

往前问"为什么没发生"，就是把 `JOIN` 那一行反过来（`t.cause = chain.id`）。

**为什么这是整个设计里最关键的一段**：这正是选 SQLite 换掉"自己写文件格式"的**唯一最大理由**。
一行一条的文件里，往回走一步就得扫一遍文件——**八跳的链子要扫八遍 89MB**。
这里是**一句查询走完全程**，而且走的是索引。

**会不会绕成一个圈走不出来**：不会。`CHECK (cause < id)` 已经从结构上挡死了——
**因必须早于果，成环就意味着某条记录是自己的祖先，那要求它比自己早。**
`depth < 64` 是第二道保险，防的是数据从别处被硬塞进来的情况。

# 三、噪音怎么办（U9）

**问题**：旧账本 8 月 12862 条里 **98.5% 是自动产生的**，值得一看的一整个月只有 **194** 条（其中"你说了一句话"5 条，而同月给时钟记了 5357 笔）。

**不要聪明的过滤器。** 判断"这条值不值得看"要是留到读的时候再猜，就会猜错——
而且猜错的方式还不稳定（今天这条被过滤了，明天没有）。

**成熟做法：写的时候就标好。** syslog 从 1980 年代起就是这么干的——每条日志自带级别，
读的人说"给我 warning 以上"，不需要任何人去猜。

**我们只要两级，不要 syslog 的八级**：

| `routine` | 意思 | 例子 |
|---|---|---|
| `1` | 例行公事 | 时钟到点、定期扫描、心跳 |
| `0` | 值得一看 | 你说的话、任务、决定、纠正、出错 |

**默认只给 `routine = 0`；要看全部就明说。**

**怎么验**：拿旧账本 8 月那 12794 条按这个规则打标，`routine = 0` 的应该落在 4% 上下。
**如果打完标发现"值得一看"的还有一半，说明规则定错了，不是数据的问题。**

# 四、不丢、不重（那条"不配当用例、只能当前提"的）

需求文档里说过：这件事一旦破了，U7 到 U14 **会同时悄悄变成错的，而表面上一切正常**。
**它是这个系统最贵的失败方式，所以这一节全部用现成的东西，一行自己的逻辑都不写。**

| 要防的 | 手段 | 谁的做法 |
|---|---|---|
| **写一半崩了，留下半条** | 一条痕迹一个事务 | **预写日志**（ARIES，1992）。SQLite 内建 |
| **同一件事记两遍** | `idem` 列加唯一约束；重复写返回原来那条，不报错 | **Stripe 的幂等键**。写入方算一个键（比如"这条消息 + 这个动作"的哈希），数据库替你挡 |
| **边写边读，读到写一半的** | WAL 模式 | SQLite 内建。读的人看到的永远是完整状态 |
| **多个 agent 同时写** | SQLite 自己排队 | SQLite 内建（多读单写） |

**注意 `idem` 允许为空，而 SQLite 的唯一约束不管空值。** 所以：
**给了键的参与去重，没给的照常写入**——不强迫每个写入方都想清楚幂等性。

> **旧系统在这件事上其实做对了一半**：`intent_effects.py` 里的
> `logical_effect_id = sha256("feishu-reply-v1:" + 消息id + ":" + 槽位)` 就是一个标准的幂等键——
> **纯函数、同样的输入永远同样的键。** 那个做法照搬。
> **搬不得的是另一处**：`task_emitter.py` 用"两段文字像不像"当同一性判断，
> 把 numpy 2.1.0 和 2.2.0 当成了一件事。**同一性要么可计算，要么就别判。**

# 五、一年后还翻得动（U11）

**问题**：痕迹只会长。旧账本 105 天 89MB 还在涨，闲置索引涨到 589KB 没人读得动。

**两件事分开办：**

**① 翻的代价 —— 索引。** 按 `ts` / `type` / `cause` / `actor` 建索引，加 FTS5 全文。
文件大小照涨，**但查一条的代价基本不涨**。这就是拿数据库换文件的第二个理由。

**② 老数据 —— 降采样，不是删除。**

| 年龄 | 例行事件（`routine=1`） | 值得一看的（`routine=0`） |
|---|---|---|
| 近 30 天 | 原样保留 | 原样保留 |
| 更早 | **合并成"这一天有 N 次心跳"**，留计数不留每条 | **永久原样保留** |

**这是监控系统三十年的标准做法**（RRDtool 1999 起，Prometheus 至今）：
**越老的数据分辨率越低，但永远不消失。**

**为什么不是直接删**：因为链子。删掉一条被别人当 `cause` 指着的记录，
就制造了一条断链——**正好是 U7 最怕的东西**。降采样只动 `routine=1` 的，
而例行事件基本不被别的东西当作原因。
**★ 这个"基本"要实测**：降采样前先查一遍有多少 `routine=1` 的记录正被人指着。

## 5.1 遮罩投影：压缩不删东西，只往尾部追加一句"我把这些挡住了"

**一句话**：要让默认看到的东西变少，**不需要删任何一条**——往只追加的表尾追加一条"我遮住了这些"的痕迹，读的时候把它折出来。

### DSH 那边具体是什么

`packages/core/session/src/surface.ts`：

- 只追加的事件日志是唯一真相。模型看到的那一面（它叫 surface）是**在完整日志之上折出来的投影**。
- 折叠函数 `foldSurface` 顺着序号走：普通事件把自己的序号追加进列表；一条"替换"事件带 `{op:'replace', start, end}`，把列表里 `start..end` 那一段**整段换成它自己一个序号**。日志一条没少。
- 被遮住的那些，**序号不变、内容不变、永远在文件里**。
- 替换事件必须在 `sourceEventSeqs` 里**把它遮掉的每一条都点名**，被点名的必须比它早，不许重复（`assertProvenance`）。
- 查询层给每条事件贴三态标签（`session-query/src/documents.ts` 的 `classifySurface`）：
  **`current`**（现在这一面上）/ **`shadowed`**（被遮住了）/ **`log-only`**（本来就不上这一面）。
  这三个值直接当过滤项开放给搜索（`filters.ts`）。

配套两条纪律：

- **括号即锁**：`compaction/start` 与 `compaction/end` 是日志里的一对括号（`compaction/src/types.ts` 原话：`compaction/start` "holds the lock until `compaction/end`"）。开始压缩前**倒着扫日志**，谁更靠后决定状态；**扫到一个没闭合的开始就报 busy**（`compaction-basic/src/region.ts` 的 `inspectCompactionEntryState` / `assertCompactionInactive`）。
- **摘要不比被遮的短，就不许提交**：`region.ts` 的 `summarizeCompaction` 里一行——估出来的摘要 token 数 `>=` 被遮那段的 token 数，当场抛错，**这次压缩整个不落地**。

### 翻到我们这张表上是什么

**不动 schema。** 加两个类型 + 一个折叠函数：

| 加什么 | 是什么 |
|---|---|
| 痕迹类型 **`trace.masked`** | 一条普通痕迹。`basis` = 被它遮住的那些 id（**点名，照搬 DSH 的做法**），`payload.summary` = 顶替的那段话 |
| 痕迹类型 **`trace.mask.opened` / `trace.mask.ended`** | 一对括号。**只回答一个问题：上一次遮罩跑完了没有** |
| 折叠函数 **`masked(db)`** | 一句查询：把所有 `trace.masked` 的 `basis` 并起来，就是被遮住的 id 集合 |

**DSH 把"摘要"和"替换"拆成两条事件**（`compaction/summary` 只记账，真正顶替上去的是紧随其后的一条 `user/message`），
是因为它要往模型的上下文里塞一条消息。**我们没有那一面，一条就够。**

**三态怎么给**——不是新造的，是把我们已有的两样合到一处：

| 标签 | 我们这边是什么 |
|---|---|
| `current` | `routine = 0` 且不在 masked 集合里 |
| `masked` | 在 masked 集合里 |
| `log-only` | `routine = 1`——例行公事，本来就不进默认那一面（`recent()` 现在就是这么干的） |

**有一处我们比它顺**：DSH 需要 `sourceEventSeqs` 这个专门字段来记"我遮了谁"，
**我们已经有 `basis`**，而第二节那句往前走的查询本来就走 `basis` 这条边——
所以"这条痕迹后来被折进哪条摘要里了"这个问题，**不用写任何新查询，`became()` 现在就答得出来**。

**★D 括号和锁是两件事，我们分开办。** DSH 那对括号既是"完没完"的记号、**也是互斥锁**——因为它没有别的锁。我们有：

| 要办的事 | 用什么 | 为什么 |
|---|---|---|
| **互斥**（不许两个遮罩同时跑） | **文件锁**（`src/lock.ts`，`O_EXCL` + tmpfs） | 启停那边已经赢过一次的东西，跨进程有效，持有者死了会被回收 |
| **完没完**（上次遮到一半崩了） | **日志里的括号** | **文件锁做不了这件事**：它在 tmpfs 上，进程一死就回收，重启后什么都不剩；而"上次折叠没做完、这份投影不能信"必须活过重启 |

### 为什么这条对 U11 有用

U11 那句是"**翻它的代价不能跟着一直涨**"。而本节 ② 那个降采样是**真删**（`compact()` 里就是 `DELETE`）。

**★7 已经教过一次**：当初赌"例行事件基本不被当原因"，实测 501 条里有 1 条真被指着。
**遮罩把"要不要删"这个问题，从"值得一看"的那部分身上整个拿掉了**——默认看到的少了，一条都没少。

**★E 分工定死**：

| | 手段 | 为什么 |
|---|---|---|
| 值得一看的（`routine=0`） | **只遮，不删** | 它们是 U7 链子的承重部分，删一条就可能造一条断链 |
| 例行公事（`routine=1`）且没人指着 | 降采样（删 + 留计数） | 它们是体积的大头，而且不承重 |

**还有一个眼下就要用上的地方——U13 那批旧的**：旧对话里**本来就有压缩发生过**。
2026-08-16 实测：抽 400 个 codex 对话文件，里面有 **588 条 `compacted` 记录**，每条带一份 `replacement_history`。
**但它只给了"换完之后是什么"，没点名"换掉了谁"**——所以搬进来时，那段被换掉的历史对不上号。
这正是 DSH 那条"必须点名"的反面证据：**我们自己不点名，将来就是这个下场。**

### 怎么验

① 遮完之后**重跑 U7 的全部断言，必须还是绿的**（这就是 U11-3）；
② 被遮的那条，`get(id)` 仍然拿得回原文；
③ 摘要不比被遮的短时，那次遮罩**整个不落地**——表里连一条 `trace.masked` 都不该有。

**★15 "更短"用什么量，还没有答案。** DSH 量的是估算 token 数（它有 token 计量器），我们没有。
最省事的是 `length(payload)` 的字节数——**但字节不等于读的人真正付的代价**。先按字节做，这条留着。

## 5.2 检查点带水位线：冷读 = 装载"上次折到哪" + 只重放尾巴

**一句话**：把"从头折一遍"变成"从上次折到的地方接着折"，而且**这个检查点永远只是捷径，不是权威**。

### DSH 那边具体是什么

`packages/session/session-projection-cache/src/index.ts` 与 `packages/session/session-projection/src/index.ts`：

- 每个会话存**一行**检查点：`{ver（折叠算法的版本）, seq（折到第几条）, val（状态）}`。
- 冷读的梯子：拿这一行 → 算出一个下限（`restoreFloor`）→ 只从那儿往后读一段尾巴 → 折完 → 把新检查点写回去（**写回失败不管**）。
- 心态写在模块头，原话：**"a fold shortcut, never an authority: a row is possibly stale (its `seq` says how stale) but never wrong"**——可能陈旧（序号告诉你多旧），但绝不会错。所以每条写路径都是 fail-soft：**写失败只是下次冷读多重放一截**。
- 版本对不上就**整行丢掉重折**，不做迁移。
- 那个下限取的是"最低水位线**再往下一条**"，是故意的：读回来的尾巴因此能证明日志确实还延伸到那儿。**日志要是被截短过，这里当场发现，而不是把一行陈旧的当成当前的端出去。**

三条被源码明写成**承重**的约束：

| 约束 | 出处 | 为什么承重 |
|---|---|---|
| 折叠必须是**纯同步**的 `init` / `apply` / `view` 三件套，**不关心这条事件时返回同一个引用** | `ProjectionDefinition` 的 JSDoc：`All three functions MUST be synchronous (an async unit would tear the carriers' consistency cut)` | 异步会把"一致的那一刀"切碎；返回同一个引用，等于"没变"这件事零成本判得出来 |
| 状态必须是**普通 JSON** | 同上：`state MUST be plain JSON (the persisted-cache precondition)`；写的时候转不动就抛 TypeError | 存不进去的状态，检查点就是假的 |
| **带状态的事件必须携带变更后的完整状态，不能只带增量** | `session-projection` 模块头：`Whole-value event rule (load-bearing): a state-carrying log event MUST carry the complete post-change state, never a bare delta` | 这条是**水位线能成立的前提**：只带增量，就必须看过前面每一条，"从中间接着折"当场作废 |

第三条对我们尤其硬：**降采样会把老的例行痕迹折掉**。一条只写"预算 -3"的痕迹，
在它前面那些被折掉之后就再也算不出"现在是多少"；写"预算现在是 7"的那条，折掉多少前文都不影响。

### 翻到我们这张表上是什么

**新增一张小表。**

```sql
CREATE TABLE fold (
  name    TEXT PRIMARY KEY,   -- 哪个折叠：'intent_tree' / 'masked' / 'tasks' …
  ver     INTEGER NOT NULL,   -- 折叠算法的版本；对不上整行丢掉重折，不迁移
  upto    TEXT NOT NULL,      -- 折到哪条为止（trace.id）
  state   TEXT NOT NULL,      -- 折出来的状态（JSON）
  lineage TEXT NOT NULL       -- 这份库的谱系见证：MIN(trace.id)
);
```

冷读三步：

1. 读这一行。`ver` 对不上、`lineage` 对不上、或者 **`upto` 那条已经不在表里了**，就当没有，从头折。
2. `SELECT … FROM trace WHERE id > :upto ORDER BY id`——**只读尾巴**。因为 ULID 有序，**水位线就是一句字符串比较**，和 `CHECK (cause < id)` 是同一个便宜（★A）。
3. 折完写回，`WHERE upto < :new_upto`（谁折得远谁赢）。**写回失败只记一句，不往上抛**——它是捷径不是权威。

按我们的情况改了两处，理由写在这儿：

| DSH 怎么做 | 我们怎么做 | 为什么 |
|---|---|---|
| 水位线是一个单独的整数 `seq` | 直接用 `trace.id` | ULID 本身有序，**不用多存一个字段**（和第一节删掉 `seq` 是同一个理由） |
| "最低水位线再往下一条"，靠尾巴反证日志没被截短 | 直接查 `upto` 那条**还在不在** | 我们的日志**真的会短**——`compact()` 就是 `DELETE`。而 id 是主键，"它还在不在"是一次索引命中，比反证便宜也直白 |
| 每个会话一行，绑 `{createdAt, cwd}` 防止串库 | 全库每个折叠一行，绑 `MIN(trace.id)` | 我们没有会话这一层。要防的是 **U13 那次导入把库重建了**，旧检查点还赖在那儿 |

### 为什么这条对 U11 有用

本节开头说"两件事分开办"。**加上这条之后，那个分法要细一格**：

| 问题 | 靠什么 | 现状 |
|---|---|---|
| **查一条**（这件事为什么发生） | 索引 | 本节 ① 已经答了 |
| **算一遍全局**（意图树现在长什么样、哪些任务在跑、哪些被遮住了） | **检查点** | **本节 ① 一点忙都帮不上**——这类问题必须过一遍全部痕迹 |

**没有检查点，第二类问题的代价和总量成正比——那就是 U11 说的那个病本身。**

**旧库里有现成的反面教材**（2026-08-16 实测，`memory/L1_ledger/conversations/`）：
下面有 11 个 `.checkpoint.N` 文件共 **1.36 GB**，其中**一个会话自己占了 1381 MB**——
同一个会话的**整份拷贝存了五遍**。**检查点做错的代价是整个语料的 7.7%。**
一行带水位线的记录替掉的就是这个。

### 怎么验

① 同一个折叠，冷读的结果必须和"从头折一遍"**逐字节相同**；
② 把检查点行删掉、改坏、或把 `ver` 改掉，**结果不变，只是慢**；
③ 写检查点失败时，**那条痕迹照样写得进去**——检查点绝不能和痕迹写在同一个事务里。

**★16 多个写入方的时候什么时候写检查点，没定。** DSH 那套是单进程里的写回策略（事件计数 + 定时器 + 两个必写点：回合结束、会话卸载）。
**我们是多个 agent 各写各的，而且没有"回合"这个概念**，所以那两个必写点搬不过来。
谁赢那部分是定了的（`WHERE upto < :new_upto`），**什么时候写没定**。

## 5.3 进索引之前先问一句"这块有语义吗"，不认识就当没有

**一句话**：全文索引喂进去的是**按类型抽出来的语义文本**，不是 `payload` 整个；**不认识的默认返回空**，而不是"里面有字符串就当能搜"。

### DSH 那边具体是什么

`packages/session-query/session-query/src/extraction.ts`，整个文件 87 行：

- 按事件类型抽：用户消息、模型消息 → 正文；工具调用 → 名字 + 参数；工具结果 → 正文 + 错误名 + 错误码；待办 → 状态 + 内容；回合结束 → 结束原因。
- **回合开始 / 步骤开始 / 步骤结束 / 流式片段 / 请求头 → 明写返回空字符串。**
- 认不出的类型 → 空。注释原话：**`Unknown events remain non-searchable until a concrete first-party consumer defines semantics.`**
- 内容块那一层同理：**推理块**明写返回空数组；**图片块**（`image` 确实在它的块类型表里）没有分支，落到默认，**也是空**。默认那条的注释：**`Unknown blocks do not become searchable merely because their payload happens to contain strings.`**
- 抽出来是空的事件，**连一份文档都不生成**（`documents.ts`：`if (text.length === 0) continue`），根本不进索引。
- 每份文档还带着 5.1 那个三态标签，**所以搜索可以只搜"现在这一面上的"**。

### 翻到我们这张表上是什么

```sql
CREATE VIRTUAL TABLE trace_fts USING fts5(text, id UNINDEXED);
```

喂进去的不是 `payload`，是一个 `semanticText(type, payload)`：按类型抽，认不出的返回空串，**空串不进索引**。

### 为什么这条对 U11 有用

**索引的体积和建索引的时间，跟"喂进去多少字"成正比，不跟"有多少条痕迹"成正比。**

2026-08-16 实测 `memory/L1_ledger/conversations/`。**口径必须写明，不然两次测量对不上**：

| | 只算 `.jsonl` | 全部文件 |
|---|---|---|
| 文件数 / 体积 | **13502 个 / 16.31 GB** | **16733 个 / 17.63 GB**（多出的 3229 个是 `.json`） |
| 大于 50MB 的 | 50 个，占 **42.7%** | 50 个，占 **39.5%** |

中位数 **0.218 MB**（绝大多数很小）。L2 那边：**纯文本 5.87 MB**（2514 个 md）、
**全部文件 19.51 MB**（2568 个）。

> ⚠ **这个数原来写的是"L2 纯文本 28 MB"，错了 4.8 倍，2026-08-16 改。**
> 28 MB 是 `du -sh` 报的**磁盘块占用**——那底下两千多个小文件，块对齐把 19.51 MB 撑成了 28 MB；
> 而"纯文本"只有 **5.87 MB**。**量的是"装它的目录占了多少盘"，报成了"文本有多少字"。**
>
> **这正是下面那条"别量装东西的容器"，而它就犯在同一段里。** 留着不删。
>
> **⚠ 注意这次和上面 15G / 17G 那次处理方式不同，别混**：
>
> | | 是什么 | 怎么办 |
> |---|---|---|
> | **15G / 17G** | 同一批语料**在不同时间**的测量，当时都是对的 | **加注，不改数**——那是事实记录，改掉等于伪造历史 |
> | **28 MB** | **量错了仪器**，写下的那天就是错的 | **改数，并留下为什么错**——那不是事实记录，是错误记录 |
>
> **判据一句话：数当时是真的就留着加注，数当时就是假的就改掉并写明。**
> **"痕迹不改写"护的是真话，不是错话的挡箭牌。**

> **这几处的 15G / 17G / 17.63 GB 是同一批语料在不同时间的测量，语料一直在长；
> 本文自 2026-08-16 起统一用全部文件口径。**
>
> 0.5、第七节、第八节、★9、0.4 里那些「15G」「17G」**一个都没改**。
> **一个带日期的测量是一次事实记录，改掉它等于伪造历史**——
> 而这套系统整个建立在"痕迹只追加、不改写"上，**文档自己先破这条规矩说不过去**。

**近一半的体积压在 0.3% 的文件里。** 拆开最大那个（854 MB）看：

| 里面是什么 | 多少 |
|---|---|
| **base64 图片**（`"image_url":"data:image/png;base64,…"`） | **465 MB = 54.5%**，476 段 |
| 其余 base64（各种令牌、推理签名） | 27 MB = 3.2% |
| **base64 合计** | **493 MB = 57.7%** |
| 其余（命令 stdout/stderr 的原文是这里的大头） | 361 MB = 42.3% |

**一份 854 MB 的对话记录，将近六成是图片。** 命令输出是第二大项。
**这两样都是 5.3 要挡在索引外面的东西**——它们决定的是索引的大小，不是索引的用处。

**DSH 那条"图片块贡献零文本"，挡的就是这 54.5%。** 它那边这条看着像个边角料（图片本来就没字可搜），
**在我们这份语料上它是最大的一条**。

**由此得到一条抄东西的纪律，比这条机制本身更值钱**：
**抄一条机制，必须连着在自己的数据上量一遍。**
同一条规则在别人那儿的分量，不等于在我们这儿的分量——**不量，抄回来的东西轻重全错**。
按 DSH 的写法读，"图片块贡献零文本"是顺手一句；按我们的数据读，**它是这三条里最值钱的一句**。
（这条是第九节那张落账表的补充：**光记"用了谁的做法"不够，还得记"在我们这儿它有多重"**。）

> **这里有一处口径我先前搞错了，把过程留下**（沿用 U9 那条把改数过程留在文里的做法）：
> 我一开始的结论是"图片不是大头，命令输出才是"。**错了，而且是两个错误指向同一个方向。**
>
> | 错在哪 | 具体 |
> |---|---|
> | **① 探针找错了键** | 我搜的是 `"data":"<base64>`（Anthropic 那种写法），而这份记录用的是 `"image_url":"data:image/png;base64,<…>"`。**一处都没命中，我把"没搜到"读成了"没有"** |
> | **② 量的是行，不是那段字节** | 我按整行的字节数给记录类型分桶，于是**含图的那 280 行（467 MB）整个记到了"命令执行记录"名下**。所谓"130 MB 命令输出"里，绝大部分是它那一行里嵌着的图 |
>
> **正确的量法：只统计 base64 数据串本身的字节**（`[A-Za-z0-9+/]{200,}={0,2}`），不按整行算。
> 阈值提到 1000 字符结果一模一样（还是 493 MB），**说明这不是低阈值凑出来的**。
>
> **留下的教训**：一条记录常常同时装着好几种东西，**按"这行属于谁"分桶，会把一整行算给其中一个**。
> 想知道"什么占了体积"，就得量那样东西本身的字节，别量装它的容器。
> ——这和 U9 那次"分项摆在眼前却没相加核一遍"是同一类毛病：**都是拿一个方便的代理量，冒充要测的那个量。**
> 这个归类单独立成一条，见下。

### 一条量法纪律：别量装东西的容器

**单独立一条，是因为它已经犯了三次，而且还会再犯。** 三次都是**拿一个方便的代理量，冒充要测的那个量**：

| 什么时候 | 要测的 | 实际量的 | 结果 |
|---|---|---|---|
| U9 定"值得一看占几成" | 各类事件各有多少条 | 分项摆在眼前，**没相加核一遍** | 虚高约 220 条，那个数前后改了两次 |
| 这次，我 | 图片占多少字节 | **整行**的字节，按记录类型分桶 | 含图的 280 行（467 MB）整个记到"命令执行记录"名下，**结论反了** |
| 这次，复核的人 | 同上 | 按整行算，得 55.5% | **方向对，但是碰巧对的**——离正确量法只差一步 |

**判据一句话**：**要测什么，就量什么本身**，别量装它的那个容器——行、文件、记录、批次。
**容器几乎总是混装的**，按容器分桶必然把一整份算给其中一样。

**为什么它值得占一节**：这套系统里"坏了还长得像好的"是最贵的失败方式（需求文档结尾那条）。
**代理量算出来的数长得和真数一模一样**——有小数点、有百分比、能画成表。
**它不会报错，只会让你确信一件错事。**

第八节那句"17G 那部分跑两分钟超时"、★9（15G 建全文索引要多久没实测），说的都是这件事。
**语义投影是让 ★9 有可能变绿的那一步**：喂进去的从 17.63 GB（全部文件口径）降到"人真说过的话"那一档
（L2 那 **5.87 MB** 纯文本是个下限参考）。**光是把图片挡在外面，最大那个文件就少喂 54.5%。**

**这个下限比原先写的小得多**（原来引的 28 MB 是块占用，见上）——**也就是说语义投影的收益比先前估的更大**：
一头是 17.63 GB 的原始语料，另一头是个位数 MB 的纯文本。**结论方向没变，量级先前说小了。**

**★F 有一处我们必须和它反着来。** DSH 的事件类型是 TypeScript 里一张能穷举的表，`switch` 写全了有编译器盯着，**"认不出"是罕见情况**。
我们的 `type` 是一个自由的 TEXT 列，随手写个新类型就能进库——**"认不出"在我们这儿是常态**。
照抄"默认空"，就会有一批新痕迹**悄悄搜不到**，而"悄悄"正是 U8 说的那种最难查的失败。

所以：**默认仍然是空**（不让垃圾进索引），**但漏掉的必须出声**——
建索引时把认不出的类型统计出来，写成一条 `index.unknown_types` 痕迹。
它是 `routine = 0`，**所以它自己会出现在"最近发生了什么"里**。不靠谁记得去看。

中文怎么分词（FTS5 默认的分词器切不动中文，`trigram` 是候选）**这里不定**，和 ★9 一起实测。

### 怎么验

① 拿旧库里最大的那个文件跑一遍，**进索引的字数应该比原文小一到两个数量级**；
② 造一条系统没见过的类型：**它必须搜不到，而且必须出现在 `index.unknown_types` 那条痕迹里**——
搜不到但没出声，算这条**没做到**。

# 六、谁来写（U12：不靠谁记得）

**旧系统的教训**：负责回复的副本经常记得回复、忘了留痕。**后来靠在提示词里写"必须记得"来堵——那是在赌运气。**

**成熟做法：留痕是旁路截获，不是主动上报。** Unix 的做法就是这样——
程序只管往 stdout 写，捕获是别人的事，程序自己甚至不知道日志在哪。

三个来源，**前两个不需要任何人记得**：

| 来源 | 怎么进来 | 靠谁记得？ |
|---|---|---|
| **部件的输出** | systemd 的 `StandardOutput=` 直接接走 | **不需要**（启停那边已经做了） |
| **agent 的对话** | 后台扫转录文件 | **不需要**（旧系统这块已经在跑） |
| **结构化事件** | agent 经那道唯一的门写进来 | **仍然要它自己记得 ★** |

**诚实的缺口**：第三类还是要 agent 自觉。**但破坏程度有限**——
因为对话已经被截走了，**"这件事发生过"不会丢，丢的只是"这件事的结构化那条"**。
粗的兜住了，细的还漏。

**能不能补上**：能，做法也是现成的——**从转录里派生结构化事件**（就是 ETL）。
让一个后台作业读转录、抽出事件写进来。**★ 这一步先不做**，
等真的漏出问题再说；写在这儿是为了别把它当成没想过。

**唯一的门**：所有写入走同一个入口，禁止绕过去直接动库。
**这条直接照搬旧系统的 memory 契约**——那是它做得最对的一件事。

# 九、这一份设计里，哪些是别人的，哪些是我们自己造的

> **这张表就是 [`PRINCIPLES.md`](../PRINCIPLES.md) 那条原则的落账。**

**用别人成熟做法的（这份设计的绝大部分）：**

| 用在哪 | 用了谁的 | 有多老 |
|---|---|---|
| 存储、事务、并发、索引、全文 | **SQLite** | 2000 年至今 |
| 写一半不留半条 | **预写日志**（ARIES） | 1992 |
| 因果链＝每条指向上一条 | **git 的 commit parent** | 2005 |
| 唯一号且按时间有序 | **ULID** | — |
| 同一件事不记两遍 | **Stripe 的幂等键** | — |
| 噪音靠写时打级别，不靠读时猜 | **syslog 的级别** | 1980 年代 |
| 老数据降采样不删除 | **RRDtool / Prometheus** | 1999 至今 |
| 留痕靠旁路截获，不靠主动上报 | **Unix 的 stdout 传统** | 1970 年代 |
| 开场注入一份索引 | **Claude Code 自己的做法** | — |
| 所有写入走唯一一道门 | **旧 Theseus 的 memory 契约** | 本项目 |
| 压缩不删东西，只往尾部追加一句"我遮住了谁" | **DSH 的 surface 折叠**（更老的源头是数据库的 MVCC：新版本盖住旧版本，旧的还在） | 2026 生产代码 / 1980 年代 |

| 不确定要带上**是哪个操作、哪个对象** | **DSH 的 `PersistenceUncertainError`**（`operation` 是必填字段） | 2026 生产代码 |

| 该写而没写，只能事后逐条点名 | **银行对账的未达账项**（我这边记了、对面没有对上的那笔） | 复式记账至今 |

> **上面带 DSH 字样的那几行（遮罩折叠 / 检查点 / 语义抽取 / "没做成"的命名 / 不确定带操作和对象 / 不变量伴随插件）为什么值得单独说**：
> 它们是这份设计里**从一份别人的生产代码里逐行读出来的**部分，不是从概念里推的。
> 底下的想法都比 DSH 老得多（盖住不删是 MVCC、检查点 + 重放是事件溯源、写时求值是 CHECK 约束），
> **但"具体怎么落地才不出错"这一层，只有读源码才拿得到。**
>
> ⚠ 这段原话是"**唯一**从别人生产代码里读出来的"。**"唯一"已经不成立**——
> 第十节又从同一份源码里读出四条（2026-08-16，v2-u8-design 加的）。**多一处就少一分独特，这是好事，不是错。**

**★ 自己造的，七处**，每一处都值得被单独盯着：

| ★ | 自己造的 | 为什么没有现成的 |
|---|---|---|
| **★A** | **`CHECK (cause < id)`** ——用"因必须早于果"挡住成环 | 因果序的想法是老的（Lamport），但**把它压成一句字符串比较**是这里的具体做法。**它替掉了本来要写的一整套环检测。这是最划算的一处** |
| **★B** | **`routine` 只要两级，不要 syslog 的八级** | 级别机制是现成的，**几级是我们定的**。理由：旧数据里"值得一看"的只占 4%，两级够分 |
| **★C** | **哪些类型算例行** | 这是这个系统特有的判断，没有别人能替我们定 |
| **★D** | **括号只管"完没完"，互斥交给已有的文件锁** | DSH 把两件事合成一件，因为它没有别的锁。**我们有，所以拆开**：文件锁在 tmpfs 上，进程一死就回收，答不了"上次跑到一半崩了没有"；日志里的括号答得了。见 5.1 |
| **★E** | **遮罩只用在 `routine=0`，删只用在 `routine=1`** | 这个分工是我们定的，依据是 ★7 那次实测（赌"基本不被指着"，实测有被指着的）。DSH 没有这个二分 |
| **★F** | **不认识的类型不进索引，但必须出声** | DSH 那边"认不出"是罕见情况（类型能穷举，编译器盯着）；**我们这边是常态**（`type` 是自由文本）。默认照抄，出声是加的。见 5.3 |
| **★G** | **10.3 那棵判据树**——一个请求现在怎么样了，五种结果之间怎么选 | **五种结果每一种都是抄的**（见 10.1），**但"怎么在它们之间选"是我们定的**：DSH 每一处只面对自己那一种，从来不需要选。**这也是最容易定错的一处，所以它可扫：五种各造一次，必须得到五个不同的答案（U8-5）** |

**七处都很小，而且都可验证。** 除此之外这份设计里没有一处是新发明的。

# 十、「没发生」和「不确定」要有名字（U8）

**一句话：把"决定不做"当成一件发生了的事来记。** 它有类型、有时间、有依据，和"做了"的痕迹长在同一张表里，用同一个方式查。

## 10.1 先按第一原则问：这是新问题吗？——一半是，一半不是

去 **DSH**（DeepSeek Harness，deepseek 自己写的 agent 运行壳，源码在 `refs/deepseek-harness`）里翻了一遍。

**它没有 U8 这样的通用能力。** 你在 DSH 里问不出"这件事为什么没发生"——没有这个入口，也没有一张"没做的事"的表。

**但同一条原则，它在六个互不相干的地方各自落地了一遍。** 六处的形状一致得不像巧合，所以那条原则可抄；它没做的那一步——**把六处收成一个机制**——正是我们要做的事。

先解释两个词，后面一直用：**落盘** = 写进磁盘，断电也还在；**屏障** = 一句"等到真写进磁盘了再往下走"的等待。

> **本节所有行号以 `abe560f8`（`0.1.0-rc.5`，2026-08-13）为准**——`refs/deepseek-harness` 是活克隆不是快照，声明见第五节 DSH 引子。
> 翻回来核对：`git -C refs/deepseek-harness show abe560f8:<路径>`。

> 下面是**八行、六处**：崩溃恢复和定时提醒各占两行——**一行讲它凭什么这么分，一行讲它交出去的东西长什么样。**

| 它在哪 | 给"没发生"起的名字 | 关键在哪（这才是要抄的） |
|---|---|---|
| **崩溃恢复**<br>`packages/core/session/src/repair.ts:16` | **`TOOL_OUTCOME_UNKNOWN`**（结果未知） | **它分的不是"做没做"，是"落盘了几件"。** 调用记下了、结果没记下 → 结果未知；调用都没记下 → 根本没开始（`TOOL_NOT_STARTED`）。判据就是 `repair.ts:92` 一句 `const started = callSeq !== undefined` |
| 同上，写给模型的那句话<br>`repair.ts:104` | 明说"不知道"，并**禁止盲目重试** | 原话：「…Its outcome is unknown. …retry only if the operation is read-only or idempotent; if it may have side effects, first verify external state or ask the user. **Do not retry blindly.**」——**它没有替人做主，它把选择连同不确定性一起交回去** |
| **定时提醒的读和写**<br>`packages/schedule/schedule/src/tools.ts:204` | **`persistence_uncertain`**（这一笔落盘不确定） | 屏障没过时**不回答业务问题**：列表不返回列表、删除不返回"没找到"（`tools.ts:407` / `:433` 先 `preflight`，不过就直接返回，连折叠都不做）。**"我没确认"绝不伪装成"没有这条记录"** |
| 同上，错误对象的形状<br>`packages/schedule/schedule/src/types.ts:172` | 不确定里**带着是哪个操作、哪个对象** | `{ code, message, operation, id? }`，`operation` 必填。**一句"落盘不确定"没用，"创建 id=schedule-1 那一笔落盘不确定"才有用** |
| **工具调用被取消**<br>`packages/session/session-checkpoint-policy/src/index.ts:47` | **`ABORTED_BEFORE_DISPATCH`**（还没开始就被取消） | 和"开始了才被取消"分成两个码。**前者保证没有副作用，后者不保证。** 一个码装两种，等于两种都不知道 |
| **工具超时**<br>`packages/guard/timeout-policy/src/index.ts:25` | **`TOOL_TIMEOUT`**，且**分清是谁的表响的** | 拿自己的码去认自己的定时器（`:73`）。外层套着的那个先响时，读出来是普通的上游取消——**不冒充自己超时**。谁喊的停，本身就是要记的信息 |
| **压缩摘要**<br>`packages/compaction/compaction-basic/src/region.ts:374` | 摘要不比原文短，就**拒绝提交** | 一句 `framedSummaryTokenCount >= prepared.shadowedTokenCount` 就抛。**做了但没效果 = 没做**，不许算成做了 |
| **结果太长要换成摘要**<br>`packages/spill/spill-policy/src/index.ts:184` | 换完可能更长时，**放弃换，保留原文** | 先给告示预留字节（`:171`），换完还超上限就整个放弃，注释原话 `keep the inline content`。**宁可超，不撒谎** |

**六处的共同形状，一句话**：**每一次"没做成"都被起了名字，而且那个名字自带"我知道多少"。**
不是"失败"，是"没开始 / 结果未知 / 落盘不确定 / 摘要没变短"。

**这正是我们缺的东西。** 旧系统里对应位置全是同一个东西——**什么都没有**。

## 10.2 我们的做法：给"不做"开一批类型，每条带依据

**不新造机制。** 痕迹表在了，`record()` 那道门也在了。要加的只有两样：**一批类型名**，和**用这些类型时必须一并交出来的东西**。

| 类型 | 中文 | 除了依据，还必须带什么 |
|---|---|---|
| `decision.skipped` | 决定不做 | —— |
| `decision.deferred` | 决定推迟 | **什么条件下会再来**。说不出条件的，它不是推迟，是不做 |
| `decision.merged` | 判定重复而合并 | **留下的是哪一条、被并掉的是哪一条、当时凭什么判成同一件** |
| `decision.dropped` | 请求被丢掉 | **是哪一种丢**：队列满 / 超时 / 关机 / 上游撤回 |
| `outcome.unknown` | 结果未知 | `cause` 指向**那条已经落盘的"我开始做了"**。没有那条，它就不是"未知"，是"没开始" |
| `persistence.uncertain` | 落盘不确定 | **是哪个操作、哪个对象**（照抄 DSH 的 `operation` + `id`） |

**为什么用 `decision.` 这个前缀，而不是随便起名**：因为门里已经写着这一条——

```
src/trace.ts  record()   if ((isDecision(m.type) || isConclusion(m.type)) && grounds.length === 0) 拒
```

**四种"决定"一挂上这个前缀，"不带依据就写不进来"是白捡的，一行新代码都不用写。** 这是这一节最划算的地方。

**`outcome.unknown` 和 `persistence.uncertain` 挂不上这个前缀**，因为它们不是决定——**它们是"我不知道"**，而"我不知道"没有依据可言。
它们要交的是**指向那件不确定的事的手指**：前者用 `cause` 指住"我开始做了"那一条，后者在正文里点名操作和对象。
**这两条现在只有约定、没有强制**（★18 说的是同一件事的一般形态）；而且 **`outcome.unknown` 眼下根本写不出来——还没有写入方，见 ★23。**

## 10.3 判据：五种结果之间怎么选

**分类不给判据，等于没分类。** 判据只有一根轴——**不是"发生了什么"，是"我知道多少"。**

```
我提的这个请求，现在怎么样了？
│
├─ 我连"有没有记下来"都不确定 ─────────→ persistence.uncertain
│                                          （带上是哪个操作、哪个对象）
├─ 记是记下来了，但不知道做完没有 ─────→ outcome.unknown
│                                          （不自动重做；要人确认，或去查真实状态）
└─ 我确定它没做
   ├─ 以后还会再来一次 ────────────────→ decision.deferred（写死再来的条件）
   ├─ 有另一条正在替它办 ──────────────→ decision.merged（点名替身 + 判定依据）
   ├─ 系统判定它不该做 ────────────────→ decision.skipped（写判定依据）
   └─ 以上都不是（队列满 / 超时 / 关机）→ decision.dropped（写是哪一种）
```

**每一层都是一个是非题，写的人当场答得出。** 判据就该长这样——**要是需要斟酌，它还不是判据。**

**头两层的分界线是抄来的**，就是 DSH 那句 `const started = callSeq !== undefined`：
**你手上有没有一条已经落盘的"我开始了"，决定了这件事归"未知"还是归"没开始"。**

**★G**（已落账在第九节）：五种结果每一种都是抄的，**这棵树是我们自己造的**——DSH 每一处只面对自己那一种，从来不需要选。

## 10.4 走一遍 numpy：人是怎么查出来的

当年真实发生的：两个请求文字够像（95.5%）就被当成同一个，**numpy 2.2.0 那条一声不吭地没了**。
它最后是**被人去读代码读出来的**，不是被查出来的。

**换成这套设计，同一件事在表里长这样**（三条痕迹，都是真事件，不是注释）：

| # | 类型 | `cause` | 正文里有什么 |
|---|---|---|---|
| ① | `task.requested` | 起点 `you-said` | 装 numpy 2.1.0 |
| ② | `task.requested` | 起点 `you-said` | 装 numpy 2.2.0 |
| ③ | `decision.merged` | **指向 ②** | 留下的是 ①、被并掉的是 ②、相似度 0.955、用的是哪条规则；`basis` 里放 ① 和那条规则的痕迹 |

**为什么 ③ 的 `cause` 指被并掉的那条，而不是留下的那条**：因为这条决定是**关于被并掉的那一个**的。
一次合并并掉了三条，就写三条 `decision.merged`，一条一个。
**这样 `cause` 永远只有一个指向，不必为"合并有两个输入"专门发明什么东西。**（简化准则：能不发明就不发明。）

**于是人有两条路查得到，走哪条都行：**

**第一条——我知道该去问它。** 问"我提的 numpy 2.2.0 后来怎么了"，就是 `became(②)`（第二节那句往前走的查询）。一跳命中 ③，答案是：

> **「它被判定成和 numpy 2.1.0 是同一件事而合并了。相似度 0.955。留下的是 2.1.0 那条。」**

**第二条——我根本不知道有东西被吞了。** 这才是当年的真实处境：**没有任何人知道该去问 2.2.0。**
所以还得有另一句问法：**"最近有哪些要求，既没被办、也没有一条说明它为什么没被办？"** 见 10.6。

> **第一条路今天就已经通了。** `became()` 走两种边——"谁把它当上一步"和"谁把它当依据"（`src/trace.ts` 里那句 `FORWARD` 查询）。
> 那段注释里已经写着为什么要走第二种：**"被并掉的那个不是任何人的上一步——而那正是当年 numpy 2.2.0 一声不吭消失的位置。"**
> **这一节做的事，是把那个位置真的填上一条记录。查询早就等在那儿了，一直缺的是被查的那条东西。**

## 10.6 缺席查不出来，只能扫

**"决定不做"要留痕，前提是有人真写了那一条。** 什么保证有人写？**没有保证。**

**而且这个洞补不上，原因很硬**：写入前校验（十一节）能拦下"写进来的东西不对"，**拦不下"该写的东西没写"**——
**缺席在写的那一刻并不存在，没有任何一次写入可以被拦。**

**能做的只有事后扫，而且这有成熟做法：银行对账里的"未达账项"**——我这边记了一笔、对面没有对上的那一笔，逐条列出来点名。
不是找错，是**找对不上的**。（`PRINCIPLES.md` 把"双向对账"列为这个系统必须自己写的四样之一，这是它的一个实例。）

**落到我们这儿是一句查询**：一条进来的请求，过了一段时间之后，**既没有任何后继，也没有任何一条"不做"指着它**——就是一条静默失踪。

```sql
SELECT id, ts, type FROM trace t
 WHERE t.type LIKE '%.requested' AND t.ts < :cutoff
   AND NOT EXISTS (SELECT 1 FROM trace c WHERE c.cause = t.id)
   AND NOT EXISTS (SELECT 1 FROM trace c, json_each(c.payload,'$.basis') j WHERE j.value = t.id);
```

**这两个 `NOT EXISTS` 就是 `became(id)` 返回空**——第二节那句往前走的查询走的正是同样两种边。
**同一段逻辑，一处写法：正着用是回答，反着用是报警。**

**它满足验收那份文档要求的两关：**

| | 答案 |
|---|---|
| **它什么时候会说"不"** | numpy 2.2.0 那条会出现在结果里。当年那件事**当天就会被喊出来**，不必等人去读代码 |
| **它会不会冤枉人** | **会，如果 `:cutoff` 定错。** 一个还在排队的请求会被当成失踪，几次之后就没人当回事了。**★20** |

**★19** 记的是这个洞本身：**没有任何东西保证"决定不做"那一条真被写下来**，兜底只有这个事后扫描——
而事后扫描比写时拒晚一步，**"拒是当场看得见的，扫是一轮之后才看得见的"**（U10-4 那条的原话，同一个道理）。

# 十一、写入前校验：给只追加的表加 CHECK 约束

**一句话：在写的那一刻判定合法性，不合法就写不进去。** 不是写完再查，不是定期扫。

先解释一个词：**CHECK 约束**是数据库自带的一条规矩，**在写的那一刻求值，不合规就拒绝这次写入**。
**"只追加的表"**是只往后加行、不改也不删的表——我们的痕迹表就是。

**这不是新东西，我们已经在用了，只是从来没给它起过名字：**

| 已经在用的 | 它在写的那一刻求什么值 |
|---|---|
| `CHECK (cause IS NULL OR cause < id)` | 因必须早于果 → **因果成环从结构上不可能** |
| `idem` 的唯一约束 | 同一件事不能记两遍 |
| `record()` 里 205–231 那一串拒绝 | 没有上一步也说不出起点种类的、上一步不存在的、决定不带依据的、结论依据全是例行的——**全在 INSERT 之前拦下** |

**这一节做的事，是把这三样认成同一样东西，并定下"往哪儿加"的规矩。不加代码，加判据。**

## 11.1 DSH 的做法，以及它做对的那个细节

**DSH 给每个包配一个"不变量伴随插件"**（invariant companion，就是一个专门放校验的小插件）。
它监听事件派发，**拿到候选事件后，用 `[当前全部事件 + 这一条候选]` 跑一遍完整折叠**——
**折叠**就是把一串事件从头过一遍算出当前状态——**折不通就抛**。

```ts
packages/schedule/schedule/src/invariant.ts:38   ctx.on('internal/dispatch', (_mode, eventName, args) => {
:42                                                 validate([...session.events, event], …, fail)
```

**关键在挂在哪个点上。这个细节值得单独抄，因为选错了就从"拒绝"变成"记一条日志"：**

```
packages/core/session/src/index.ts   append()
  :641   callbacks = collectSessionCallbacks(…)   ← 这一句里面 emit 了 internal/dispatch
  :643   this.log.push(event)                      ← 事件在这一行才真的进表
  :646   invokeContainedSessionObservers(…)        ← 已发布的 session/event 到这里才跑
```

**挂在 `internal/dispatch` 上抛**：异常顺着 641 一路抛出 `append()`，**643 那行永远不执行——表没动过。**
**挂在已发布的 `session/event` 上抛**：没用。`invokeContainedSessionObservers`（`:381-399`）把每个监听器的抛**全部吞成一条 warn**。

**同一份校验，挂前面是拒绝，挂后面是抱怨。**

**还有一步更狠的，钩子那个包做了**（`packages/hooks/hook-protocol/src/invariant.ts:100-111`）：
校验过的候选先**暂存**起来，等它真发布时再核对一遍"这条是不是我校验过的那条"；不是的就报
`hook event published without pre-commit validation`。**校验自己也被校验**——防的正是"有人绕过了拦截点"。

**我们对应的位置**：这道门（`src/trace.ts`）是唯一入口，**但"它是唯一入口"现在只是一句约定**，没有任何东西在拦绕过去直接动库的写入。**★21。**

## 11.2 配套那条制度值得抄：强制做决定，而不是默认沉默

**DSH 的门禁**（`scripts/package-invariants.ts`）要求：**每个包必须有一个伴随插件。**

| 门禁拦什么 | 在哪 |
|---|---|
| 没有伴随插件 | `missing package-owned invariant companion` |
| 用生成器生成的模板 | `:174` —— 带 `@generated` 记号一律拒，**必须手写** |
| 空的校验但不解释 | `:269` —— **空的可以，但必须带一句 `No runtime invariant:` 开头、针对本包的解释** |
| 写了校验却没用上报错器 | `:284` —— 假装校验的也拒 |

**实测这条制度跑出来的样子：**

| | 数 |
|---|---|
| 包总数 | **219** |
| 有伴随插件的 | **219（一个不落）** |
| 其中明说"这里没有可查的关系，因为……"的 | **184（84%）** |
| 真的写了校验的 | **35（16%）** |

**84% 是空的——这不是这条制度失败了，这正是它的产出。**
它要的不是"每个包都有校验"，是**"每个包都回答过这个问题"**。
**一个包写下"我这儿没有可查的关系，因为 X"，和一个包压根没想过，在文件里长得完全不一样。**

**落到我们这儿**（我们没有"包"这个东西，这条制度的外壳抄不动，内核能抄）：

> **每加一个新的痕迹类型，必须回答一句"它写进来之前查什么"。答案可以是"什么都不查"，但必须写下来为什么。**

**这是一张类型登记表**，一种类型一行，缺一行就红。对应验收那边的 **U8-12**。
**★22：这张表现在还没有扫描器**，只能靠人看——**而"没人去看"正是它会失效的方式**（★11 那条的原话，同一个病）。

## 11.3 什么该进写入前校验，什么不该

**判据一句话：能在"这条候选 + 已有的全部"里算出真假的，进；需要看外面世界的，不进。**

| 进 | 不进 |
|---|---|
| 决定不带依据 | 依据说得**对不对**（要看外面） |
| 合并不点名被并掉的是谁 | 那两件事**是不是真的**同一件——**这正是当年出事的那个判断，它算不出来** |
| 推迟不写再来的条件 | 那个条件**合不合理** |
| 因果成环、上一步不存在、同一件事记两遍 | 该写的东西**没写**（缺席，见 10.6，只能事后扫） |

**右边那列不是"以后再做"，是"这里做不了"。** 混进来会得到一个假绿灯——
**正是验收那份文档一整节在讲的那个病：一个只看形式的检验，会被形式满足。**

## 0.4 U14 怎么"找相关内容"：agent 自己搜，不另造机制

**2026-08-09 游渊定：不需要专门的相似度机制，agentic search 就够。**

拆开看，U14 其实要两半，**两半都不需要"判断两句话像不像"**：

| | 谁发起 | 怎么做 |
|---|---|---|
| **开场那一份** | 系统推给 agent | 新会话开始时，把"你该知道的"直接放到它面前。**这里没有相似度判断**，就是给它一份索引 |
| **中途要用时** | agent 自己拉 | agent 觉得需要就自己去搜。**这就是 agentic search** |

**为什么这样就够**：判错的代价小。找不到，人再问一句。
对比当初被否掉的那个用法（判断两个任务是不是同一个）——**那里判错会让任务静默消失**。同一类判断，代价差着量级。

**但它有个硬前提，必须写在这儿**：agentic search 只在**翻得动**的时候成立。
**实测**：查 Theseus 记忆时，小的那部分（L2，**纯文本 5.87 MB**）秒出，**大的那部分（17G）跑了两分钟超时，只能放弃**。
（**原标"28M"是 `du` 的块占用，不是文本量，2026-08-16 改**；见 5.3。**观察本身没变。**）
**所以 U14 不是独立成立的，它挂在 U11（翻一遍的代价不能一直涨）上面。U11 塌了，U14 跟着塌。**
