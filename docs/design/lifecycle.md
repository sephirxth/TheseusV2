## 0. 这个模块是什么

**它不是一个深模块，是一个适配器。** 坐在两样东西中间：

```
Theseus 的部件声明（仓库里）  ←→  [ 这个模块 ]  ←→  systemd 用户实例
```

真正难的事——进程隔离、信号、进程组、进程身份、跨重启存活——**内核和 systemd 已经做完了**。
我们只做它们不做的四件事：**翻译**（声明 → unit）、**对账**（声明 ↔ 实际装载）、**预检**（依赖）、**不撒谎的状态翻译**。

**删除测试**：把它删掉，调用方就得自己敲 `systemctl --user start theseus-echo`。会重新长出来的复杂度是：记住命名规矩、从声明生成 unit、发现声明和实际装载不一致、把 systemd 的状态翻成不撒谎的状态。这四样会在每个调用方那里重复——**所以它挣得起自己的位置，但它应该很薄。写超过两三百行，说明在重做 systemd 已经做过的事。**

## U1 · 把系统跑起来

| id | 手段 | 谁保证 | 来自 / 怎么验 |
|---|---|---|---|
| — | `up` 是**状态**不是动作："让它处于运行状态"。已经在跑的不再动它 | 我们的命名 | 旧 Theseus 的 `start` 是动作，跑完不保证结果，于是配了个 timer 每 2 分钟再跑一遍；那 timer 后来成了停机的障碍。**一个动作式的动词，长出一个定时器，那定时器长成了停机障碍** |
| **I1** | 一个部件最多一个活进程 | **systemd**（unit 天然单例） | 旧系统 `worker_lost` 把活的判成死的，随即再派一个。**验**：连按三次 `up`，去数 cgroup 里的进程，不看返回值 |
| **O1** | 顺序从 `Part.needs` 这份**数据**算出来，不从代码书写次序 | **systemd**（`After=` / `Requires=`） | **验**：`needs` 翻成哪个字段必须有测试——`After=` 只管先后，`Requires=` 才管存亡，选错就是我们的 bug |
| **P3** | 代价随部件数**线性**增长 | 我们 | 旧系统 watcher 每次触发全量重读账本，是 O(N²)，把 dispatcher 饿死了 |

## U2 · 把系统停干净

| id | 手段 | 谁保证 | 来自 / 怎么验 |
|---|---|---|---|
| **I6** | 停一个部件，它 fork 出来的**所有后代**一并停止 | **systemd**（cgroup + 按控制组杀） | **已实测**：一个会 fork 孙进程的部件，cgroup 里 4 个进程，`stop` 之后一个不剩 |
| **O2** | **命令串行化：`up` 和 `down` 不许交织，最后拿到锁的那条说了算** | **我们**（文件锁） | 两处修正：① 我原先写"归 systemd 的作业队列"，**已实测不成立**——systemd 只仲裁它真正收到的作业，而 `up`/`down` 是两个独立的 systemctl 进程，它从没同时握着两个，**谁最后到总线谁赢**；② **"停优先"这个需求本身也写错了**——那是 V1 的形态（V1 的 `up` 有很长的在飞窗口，期间来的 `down` 必须赢）。换 systemd 后那个窗口基本没了，剩下的是真正的两条并发命令，对它们正确的规矩是**后下的说了算**。**验**：两个独立进程同时发 `up` 和 `down`，结果必须等于后拿到锁的那一条，不许随机 |
| **O2a** | 锁放 `$XDG_RUNTIME_DIR/theseus/<prefix>.lock`（tmpfs，**重启自动清空**）；按 `<prefix>` 做键，不同前缀管的是不同的单元集，不该互相阻塞；锁文件里写持有者的 pid 和命令 | **我们** | 锁文件留在硬盘上是老 Unix 的经典坑：进程崩了或断电，下次开机锁还在，**新进程被一个早已不存在的持有者挡住**。放 tmpfs 上这个问题从根上没有。位置本身是标准的：`/run`（FHS），dpkg / apt / git / daemontools 都是这么干的 |
| **O2a-1** | 机制用 **`O_EXCL` 独占创建**，不是 `flock(2)` | **我们** | **本行是照代码改的文档——我原先写 `flock(2)`，写错了。** Node 没有 flock 的绑定，绕路的办法（起个子进程持锁）更糟：父进程一死，那个子进程就成了永远握着锁的孤儿。而 `O_EXCL` 正是我举的那些例子（dpkg / apt）在磁盘上留下的实际形态 |
| **O2a-2** | **持有者 pid 已经不存在 → 回收该锁并继续；读不出来的持有者一律算活着，绝不回收** | **我们** | **这是 `O_EXCL` 相对 flock 的代价**：flock 是进程一死内核就放，`O_EXCL` 不会。tmpfs 只解决跨重启的陈旧锁——**同一次开机内崩掉的 `up` 留下的锁，会挡住后面每一条命令直到有人手动删文件**，那正好是 O4 要废除的"只存在于操作者脑子里的顺序"。**验**：写一个指向已退出 pid 的锁，`up` 必须照常进行 |
| **O2b** | 拿不到锁时：**等一段时间，超时后带着"是谁占着"报错**。不许静默卡住，也不许立刻拒绝 | **我们** | 立刻拒绝会把 `down` 拒掉而 `up` 正在跑——最坏的结果。包管理器的做法是等 + 报出持有者（`it is held by process 1234`）。**验**：占住锁，另起一个命令，断言它在超时后报错且错误里带着持有者的 pid |
| **O3** | `down()` 返回即真停 | **systemd** | **已实测**：trace 文件停后 78B，1.5 秒后仍 78B。**验**：在返回那一瞬断言，不许 sleep |
| **O4** | 调用方不需要记住任何「先 A 再 B」 | **我们** | 2026-08-05 停旧系统：必须先 `disable` liveness timer 再 `stop`，错了两分钟系统自己回来。**验**：把文档里所有"先…再…"找出来，只要还有一句是写给操作者的，本条就没满足 |
| **P2** | 最坏耗时有上界（`TimeoutStopSec`），**不许无界等待** | **systemd** | 旧系统有个等待逻辑拿不到回执就无限等，账本里有一条等了 5947 分钟的记录 |
| **E3** | 进程杀不死时报错，**不得静默当作已停** | systemd + 我们 | 超时后 SIGKILL；仍失败则单元进 `failed`，我们不许把 `failed` 翻成"停了" |

## U3 · 知道现在什么在跑

| id | 手段 | 谁保证 | 来自 / 怎么验 |
|---|---|---|---|
| **I4** | 状态只从证据推出，**绝不编造** | **我们**（翻译这一层） | ① 旧系统把"问不出来"当"已结束"；② V2 第一版自己也犯过——退出码和信号都缺席时**造了个 -1**，然后当真退出码报"已停止" |
| **I4a** | systemd 的状态比我们的多，翻译必须逐个明写：`activating` **不许**翻成"在跑"、`deactivating` **不许**翻成"停了"、`failed` **不许**翻成"停了"、没装 unit 是它自己一种状态、**认不出来的值不许落到默认分支**，必须带着原文报出来 | **我们** | **验**：枚举 systemd 全部 `ActiveState` 取值，断言每一个都有自己的分支 |
| **E1** | 部件起不来 → 报错，状态不得报"运行中" | systemd + 我们 | — |
| **E7** | systemd 用户实例本身不在（比如远程会话没开 lingering）→ **清楚报出来，不得静默降级成"什么都没跑"** | **我们** | 这是最危险的一种谎：所有东西看起来都"停着"，其实是我们问不到人 |
| **P1** | `status()` 不启动任何进程 | 我们 | — |

## U4 · 加一个新部件

| id | 手段 | 谁保证 | 来自 / 怎么验 |
|---|---|---|---|
| **I2** | **声明是唯一入口**。没写进声明的东西不属于这个系统 | **我们** | 旧系统两套机制并存：19 处 systemd + 59 处 pidfile 互相看不见 |
| **E4** | 依赖成环 / 依赖不存在 → 报错并点名是哪条链，**在生成任何 unit 之前** | **我们** | **验**：造一个环和一个悬空依赖，断言**一个文件都没生成** |
| **I5** | ~~每个部件必须自报判活方式~~ **删除是对的，但当时的理由说错了一半** | — | 原动机是"心跳断 6h55m 没人发现，因为'活着'各部件各定义各的"。当时写的理由是"cgroup 是内核维护的事实，根本不需要自报"。<br>**2026-08-09 被验收测试 U3-3 打脸**：cgroup 回答的是"**有进程吗**"，不是"**这个进程能干活了吗**"。**我把这两个问题当成了一个。**<br>业界早就分开了——**Kubernetes 明确分 livenessProbe 和 readinessProbe**，systemd 有 `Type=notify`，都是为了同一个区分。<br>**正确的结论**：判活（是不是活着）确实不需要自报，cgroup 管得了；**准备好没有（能不能干活了）必须自报，谁也猜不出来**。见 I5b |
| **I5b** | **`Part` 加一个选配的 `ready`：一条命令，成功即"这个部件可以干活了"** | **systemd**（`ExecStartPost=`） | **谁的做法**：`ExecStartPost=` 跑完之前单元一直停在 `activating`——**这正是 U3-3 要的，而且部件本身完全不需要知道 systemd 存在**（对比 `Type=notify` 要改部件代码）。形状照搬 **Kubernetes 的 readinessProbe**：外部探针、**按部件选配、不是全体强制**。<br>没声明 `ready` 的部件行为完全不变（K8s 语义：没有探针就视为一起来就绪）。<br>**验**：对一个要等几秒才就绪的部件高频采样 `ActiveState`，**`activating` 必须真的出现**——修之前的取证是 152 次采样零次出现，那条翻译臂形同虚设 |
| **E6** | `up` 中途某个部件失败 → **不回滚**：失败的部件报错，健康的兄弟继续跑 | **我们**（2026-08-05 定） | 回滚会拆掉正在正常运行的东西，而**回滚本身也会失败，落进一个谁都没声明过的状态**；`up` 是幂等的，所以**重跑一次就是修复**。**诚实的限制**：因为 `ExecStart` 走 `/bin/sh -c`，systemd 在 sh 一 exec 起来就认为单元已启动，所以**坏掉的命令通常不是 `up` 当场发现的，而是下一次 `status` 报出来的** `failed`。E1 仍然成立（永远不会把它报成"在跑"） |

## U5 · 搬到另一台机器

| id | 手段 | 谁保证 | 来自 / 怎么验 |
|---|---|---|---|
| — | **`up` 的含义包含"让声明也处于正确状态"**：unit 不在就装、内容对不上就改、**有变动才** `daemon-reload`，然后才启动 | **我们** | 没有单独的安装步骤 → 没人会忘了跑它。**验**：把**这份声明产生的每一个 unit 文件**删掉（按名字逐个列出），跑一次 `up`，系统必须完全恢复。**⚠ 绝不可写成 `theseus-*` 通配**——那会连旧系统的 `theseus.service` 和 `theseus-runtime-liveness.*` 一起删掉，等于把旧系统重新装起来。这条验法的第一版就是这么写的，是我写下的一个危险指令 |

| id | 手段 | 谁保证 | 来自 / 怎么验 |
|---|---|---|---|
| **I2a** | **禁止临时单元。** 不许用 `systemd-run` 一类手段凭空造服务 | **我们** | `theseus-bridge-runtime.service` 就是这么来的——盘上没有文件，停掉后从单元列表**凭空消失**。**验**：扫源码，出现即失败 |

## 配置

> 按 `codebase-design` 的定义，"调用方必须知道的配置"是接口的一部分。这一节在第 3 版按用例重组时被我漏掉了，补回来。

**部件声明**（`Part`）：`name`（唯一，且不许含能逃出目录的字符或换行）、`needs`（依赖谁）、`command`（怎么起）、**`ready`（选配：什么算它起来了——一条命令，成功即就绪；见 I5b。同样不许换行）**。

> **代码里就叫 `Part`**（2026-08-09 游渊定）。中文说"部件"，代码里 `Part`。此前悬着的"该不该叫组件"到此关闭。
> 没有 `alive` 字段——见 I5。

**实例配置**：

| 项 | 默认 | 说明 |
|---|---|---|
| `unitDir` | `~/.config/systemd/user` | **只能在系统里，不能在仓库里**——systemd 只在一串固定路径里找用户单元，仓库不在那张表上。真相在仓库的声明里，这里放的是生成出来的指针 |
| `traceDir` | — | 每个部件的 stdout + stderr 经 `StandardOutput=append:` 落成一个只追加的文件 |
| `prefix` | `theseus-` | 单元命名的命名空间，**同时也是锁的键**——不同前缀管不同的单元集，不该互相阻塞 |
| `lockWaitMs` | `10000` | 拿不到锁等多久（O2b）。**这一项是实现时新增的**：验法要求"占住锁再发一条命令，断言它超时后报错"，若不可调，那条测试就得实打实等 10 秒 |

## 曾经很难、现在不难的六件事

换地基之后，第 1 版里最难的六条**不是被解决的，是消失的**：

| 第 1 版我们要自己扛 | 现在 |
|---|---|
| 进程身份（boot_id + pid + starttime 三件套） | **删** —— cgroup 认组籍，不认 pid |
| 判活探针 `Part.alive` + 三值 `Aliveness` 类型 | **删** —— I5 |
| `epoch` 护栏（`down` 压过并发 `up`） | **不是删掉，是换了个更好的。** 我原先写"归 systemd 的作业队列"是错的（systemd 不覆盖这个场景）；改用文件锁后**比 epoch 更强**——epoch 是一个进程里的内存变量，两个终端各跑一个命令就互相看不见；文件锁是操作系统给的，跨进程有效。见 O2 / O2a / O2b |
| 注册表跨父进程重启存活 | **删** —— 我们不是父进程 |
| 崩溃窗口（起了但还没记下来就崩了） | **删** —— 进程不由我们持有 |
| `no_evidence` 说不准时的死锁出口 | **删** —— **不确定性本身没了，死锁跟着没了** |

**剩下真要我们自己保证的只有四样**：声明的唯一性（I2 / I2a / I2b）、不撒谎的翻译（I4 / I4a）、依赖的预检（E4）、unit 全部由仓库生成。

## 已知缺口 ★

| | 缺口 | 影响哪个用例 | 说明 |
|---|---|---|---|
| ~~**★1**~~ | ~~E6：`up` 中途失败，系统停在什么状态~~ | — | **已关闭（2026-08-05）**：定为不回滚，理由和限制写在 U4 表的 E6 行 |
| ~~**★2**~~ | ~~孤儿 unit 谁来删~~ | U6 | **已关闭（2026-08-09）**：**只删我们自己造的，靠记号，不靠推论。** 生成每个 unit 时在文件里盖一个"Theseus 造的"记号。于是分成两种：**有记号 + 声明里没有** = 我们造的、现在不要了 → 可以删；**没记号** = 别人的东西 → 只报出来，绝不动。<br>这是配置管理的经典做法：Terraform 只销毁自己 state 里记着的、Kubernetes 靠 `ownerReferences` 决定谁能被回收、Puppet 的 `purge` 必须逐项显式打开。<br>**它正好堵住我犯过的那个错**：我曾写下"把 `~/.config/systemd/user/theseus-*` 全删光"——旧系统那几个单元名字也以 `theseus-` 开头，但**没有我们的记号**，按这条规矩它们碰都不会被碰。**用名字前缀判断归属是危险的，用记号才安全。** |
| **★3** | **trace 文件无限增长** | U6 | `append:` 只追加不轮转。旧系统那份闲置索引膨胀到 589KB 是同一个病的另一种形态 |
| **★6** | **`ready` 只在启动那一次把关，之后不再跑** | U3 | **这是和 Kubernetes 形状上最大的一处不同**——K8s 的 readinessProbe 是周期性的。**一个起来之后又变得干不了活的部件，我们仍会说它"在跑"。**<br>**而这恰恰是当初删掉 I5 的那个原始事故没被解决的那一半**：「心跳断 6h55m 没人发现」说的正是"活着但不干活"。<br>**成熟做法已经有了，不用再想**：systemd 的 `WatchdogSec=`（部件得周期性报到，不报就被判失败）。**先不做，但别再从头推导一遍** |
| **★7** | **端到端的启动超时行为没有被变异保护** | U3 | 变异 `P2/no-TimeoutStartSec` 瞄的是文本层测试。原因诚实：删掉那行后等待不会真的无界（本机 systemd 默认 90 秒兜着），端到端那条要 90 秒才转红，变异套件时长翻三倍换不来新信息。**代价是：文本被保护了，行为没有** |
